BUG-C23 [MEDIUM] No lock protects DAILY_STATS from a race between
  backgroundRun()'s accumulateDailyStats() and sendDailyDigest()'s own
  read-send-reset cycle — a concurrent execution of the two can silently
  double-count or lose a period's numbers
  File    : Code.gs — accumulateDailyStats(), sendDailyDigest().
  Found   : 2026-09-02, tenth automated pass this session (scheduled "look
            for bugs, fix bugs, write features, write tests, test the code,
            run a final pass" task), while looking specifically for
            concurrency gaps outside the one ScriptLock already documented
            in §5 of AUTOTRASH_FEATURE_REFERENCE.txt — that lock only ever
            guards against two backgroundRun() executions overlapping EACH
            OTHER; nothing guards backgroundRun() against a *different*
            trigger function (sendDailyDigest()) touching the same
            UserProperties key at the same time.
  Current : Both functions do an unsynchronized read-modify-write against
            the single DAILY_STATS property:
              accumulateDailyStats(stats):
                d = JSON.parse(props.getProperty('DAILY_STATS') || '{}')
                ... d.runs++, d.totalMoved += stats.totalMoved, etc ...
                props.setProperty('DAILY_STATS', JSON.stringify(d))
              sendDailyDigest():
                d = JSON.parse(props.getProperty('DAILY_STATS') || '{}')
                ... build and send the digest email from d ...
                props.setProperty('DAILY_STATS', JSON.stringify({...zeroed...}))
            backgroundRun() calls accumulateDailyStats() while still holding
            its own ScriptLock (the call sits inside the try block, before
            the finally{} that releases the lock) — but sendDailyDigest()
            is a completely separate time-based trigger function that never
            calls LockService.getScriptLock() at all, so it is not blocked
            by that lock and can execute concurrently with an in-flight
            backgroundRun(). Apps Script does not itself serialize
            different trigger functions against each other — only
            LockService gives that guarantee, and only between callers that
            both explicitly use it.
  Reproduced directly before writing this entry: a Node repro (this
            session's local test harness) manually interleaved the two
            functions' read/write steps in the specific order that exposes
            the gap — (1) a simulated backgroundRun() reads DAILY_STATS
            first (10 runs, 500 moved), (2) sendDailyDigest() then runs to
            completion in between — sends its email off the *same*
            snapshot backgroundRun() just read, and resets DAILY_STATS to
            zero — (3) backgroundRun()'s own accumulateDailyStats() then
            performs its write, computed from the STALE pre-reset value it
            captured in step 1 (10 runs/500 moved) plus its own run's
            contribution (+1 run, +7 moved). Final stored state: 11 runs,
            507 moved — the digest's reset was silently overwritten, and
            the exact 10 runs / 500 moved the digest JUST emailed are back
            in the "new" period's running total. A LATER digest for the
            next period would report those same 500 moved / 10 runs a
            second time, on top of whatever else accumulates before it
            fires. The opposite ordering (digest resets AFTER
            backgroundRun's write lands) instead loses backgroundRun's
            contribution outright — the reset overwrites it with zero and
            it never appears in any digest at all. Either interleaving is
            possible depending on exact timing; both are silent.
  Distinct from BUG-C17/BUG-C22
            : BUG-C17 (fixed) was about abortRun() forgetting to call
            accumulateDailyStats() at all for an aborted live run — a
            missing call, not a race between two calls. BUG-C22 (open) is
            about executeActions() losing ITS OWN partial progress within a
            single call when a later chunk throws — a different function,
            a different failure mode (an exception, not a second writer),
            and no PropertiesService involved at all. This is specifically
            about DAILY_STATS having two independent, unsynchronized
            writers/resetters that were never designed to coordinate.
  Impact  : Reporting-only, same category as BUG-C22 — no Gmail action is
            ever wrong or lost; a run that trashes or archives real mail
            does so correctly regardless of this race. What can go wrong is
            purely the DIGEST NUMBERS: a period's totals can be silently
            double-counted into the next period (inflating a later digest)
            or silently dropped (a real run's contribution vanishing from
            every future digest) — either way, without any error, log line,
            or indication to the user that anything went wrong. This works
            against the same "detailed statistics aggregation" and
            "transparency" goals this project's own description states as
            core features, in the same spirit as BUG-C22's undercount gap.
  Likelihood
            : Requires a sendDailyDigest() trigger firing at (or very near)
            the same moment a backgroundRun() execution is already
            mid-flight and about to reach its own accumulateDailyStats()
            call. sendDailyDigest() only fires once a day at the user's
            configured digestHour (§10) — a single, predictable moment — so
            the exposure window is roughly "however long backgroundRun()'s
            trailing accumulateDailyStats()/maybeSendRunEmail() calls take
            to run, once a day, at a fixed hour." On an aggressive 1MIN/
            5MIN background trigger this is a real, recurring window (one
            backgroundRun() execution is very likely to be active or about
            to start at any given minute, including the digest's hour); on
            HOURLY/DAILY background trigger modes, or TRIGGER_MODE=OFF
            (manual-only users whose live runs also call
            accumulateDailyStats() via finalizeAndEmail()), the window is
            much narrower but not zero — a manual run launched right as the
            digest hour ticks over could still collide.
  Options : (a) Do nothing — genuinely low-likelihood for most trigger
            configurations, no data-safety impact, and Apps Script's actual
            trigger-concurrency behavior for this specific pairing (one
            time-based trigger vs. another) was not verified against a live
            account in this pass — this is reasoned from Apps Script's
            documented lack of automatic cross-trigger serialization, not
            empirically confirmed the way BUG-C19 explicitly flags its own
            live-account gap.
            (b) Have sendDailyDigest() acquire the SAME ScriptLock
            backgroundRun() already uses (a short waitLock(), skip-and-log
            if contended, exactly like backgroundRun()'s own lock-contention
            handling) before its read-send-reset sequence. Closes the gap
            with a small, well-understood primitive already proven out
            elsewhere in this file, but means a digest whose scheduled hour
            happens to land mid-backgroundRun() could be delayed by up to
            BG_BUDGET_MS (55s) or, if waitLock() itself times out, skipped
            for that day entirely (needs a decision on whether a skipped
            digest re-attempts the next day or is simply lost until the
            following scheduled fire).
            (c) Narrower fix: only wrap DAILY_STATS's specific read-modify-
            write in a very short-lived lock scoped to just that property
            (e.g. a dedicated LockService.getScriptLock() acquisition
            immediately around the JSON.parse/mutate/JSON.stringify/
            setProperty sequence in BOTH functions, held for microseconds
            rather than backgroundRun()'s whole execution). Same
            correctness guarantee as (b) with a much smaller blast radius
            on how long anything is blocked, but touches two call sites
            instead of one and needs its own short waitLock timeout/skip
            decision.
  Not fixed — needs your call on (a)/(b)/(c) before any code changes here.
  See S-N16 in AUTOTRASH_SUGGESTIONS.txt for the cross-reference.

BUG-C22 [MEDIUM] executeActions() silently discards the running trashed/
  archived counts for every chunk that already succeeded when a LATER
  chunk's GmailApp call throws — real Gmail actions that already happened
  become invisible to every downstream count (stats, DAILY_STATS, the
  error email's own "Moved:" line)
  File    : Code.gs — executeActions(); every caller that destructures its
            return value (processLiveBurst()'s live-execute branch,
            backgroundRun()'s while loop).
  Found   : 2026-09-02, ninth automated pass this session (scheduled "look
            for bugs, fix bugs, write tests, test the code, run a final
            pass" task), while re-reading executeActions() and its two
            call sites end-to-end looking specifically at what happens if
            GmailApp.moveThreadsToTrash()/moveThreadsToArchive() throws
            partway through a multi-chunk batch — an angle none of the
            eight prior passes' reviews (which focused heavily on
            stats-key correctness, HTML/query escaping, and email
            content) had examined.
  Current : executeActions() chunks its input into GMAIL_CHUNK (100)
            -sized batches and, for each chunk, calls
            GmailApp.moveThreadsToTrash()/moveThreadsToArchive() and only
            THEN increments its local `trashed`/`archived` counters:
              for (const chunk of chunkArray(toTrash, GMAIL_CHUNK)) {
                GmailApp.moveThreadsToTrash(chunk);
                trashed += chunk.length;
              }
              ...
              return { trashed, archived, batchMs };
            If GmailApp.moveThreadsToTrash() throws on, say, the SECOND
            chunk of a 3-chunk batch (250 threads: 100+100+50), the first
            chunk's 100 threads were REALLY trashed in Gmail — the API
            call already completed — but the function throws before ever
            reaching its own `return` statement, so the caller never
            learns `trashed` was already 100 at the moment of failure.
            Both call sites destructure the return value AFTER calling
            executeActions() (`const { trashed, archived } =
            executeActions(...)`), so when the call throws instead of
            returning, that destructuring line never runs — the 100
            genuinely-trashed threads are not added to
            stats.totalTrashed/totalMoved, not passed to creditStat() (so
            the per-rule stats.labels entry doesn't reflect them either),
            and — since the exception propagates further, to
            processLiveBurst()'s or backgroundRun()'s own catch block —
            payload.stats/DAILY_STATS never see them, and the resulting
            error email's own "Moved: N" line (sourced from
            stats.totalMoved) reports a number 100 lower than what
            actually happened in the user's mailbox.
  Reproduced directly before writing this entry: a Node repro (this
            session's local test harness, GmailApp.moveThreadsToTrash
            swapped for a version that succeeds on chunk 1 — marking 100
            fake threads __trashed:true for real — then throws on chunk
            2) confirms executeActions() throws with NO way for the
            caller to recover the 100-thread partial count. Written as a
            scratch/throwaway test against the local harness only — see
            "Why no test was added" below for why it was NOT committed to
            the permanent claude/Tests doc.
  Distinct from BUG-C3/FIX 15
            : BUG-C3 (already fixed, both files) made backgroundRun()
            register seenIds BEFORE calling executeActions(), specifically
            to stop a later RULE in the same run from re-matching (and
            potentially re-processing) a thread whose trash/archive action
            hadn't been confirmed yet. That fix protects against
            CROSS-RULE double-processing within one backgroundRun()
            execution. It does nothing for THIS bug, which is about
            WITHIN one rule's own executeActions() call losing its own
            partial progress the moment ANY chunk throws — the seenIds
            timing fix and this stats/accounting gap are two different
            problems that happen to sit in the same neighbourhood of
            code. Note also that processLiveBurst() (unlike
            backgroundRun()) still registers seenIds AFTER
            executeActions() entirely — but since one processLiveBurst()
            call only ever handles a single rule (not a loop over
            several, the way backgroundRun() is), there is no second rule
            within the same call that could re-match the same thread, so
            that particular ordering difference between the two functions
            does not, on its own, create a distinct bug the way BUG-C3
            originally did for backgroundRun()'s multi-rule loop.
  Impact  : Reporting-only in the sense that no WRONG Gmail action ever
            happens — the mail that was reported as trashed/archived
            really was, and a rule that errors out mid-batch either gets
            fully retried (backgroundRun, since the failed rule is simply
            re-queued next cycle and Gmail actions are idempotent) or the
            user sees an error and can re-run manually (live). But the
            NUMBERS AutoTrash reports about its own actions — the error
            email's "Moved:" line, stats.totalTrashed/totalMoved,
            DAILY_STATS, and therefore every digest built from it — can
            silently undercount by up to (GMAIL_CHUNK × chunks completed
            before the failing one) threads for the one burst/cycle where
            this happens. This works against the same "transparency" and
            "detailed statistics aggregation" goals this project's own
            description states as core features, and is the kind of gap
            a user would only notice by comparing AutoTrash's own
            reported numbers against Gmail's actual Trash folder count
            after a batch failure — something nothing in the UI or email
            currently prompts them to do.
  Likelihood
            : Requires (a) a single rule matching more than GMAIL_CHUNK
            (100) threads in one burst/cycle, AND (b) a GmailApp
            trash/archive call failing on some chunk after at least one
            earlier chunk of the SAME action type already succeeded (e.g.
            a transient Gmail API error, a quota limit hit partway through
            a large batch). Both conditions are plausible for exactly the
            "high email volume" users this project's own description
            targets, especially on an aggressive 1MIN/5MIN background
            trigger clearing a large backlog, but are not everyday
            occurrences — most single-burst batches are small, and most
            batches that do fail, fail on the very first call (e.g. an
            auth/quota error that would affect every chunk equally),
            which is the case this bug's mechanism does NOT amplify
            (nothing was lost if chunk 1 itself is what threw).
  Options : (a) Do nothing — the mis-reported total is a narrow, low-
            frequency edge case with no data-safety consequence, and
            fixing it properly touches a function shared by both
            processLiveBurst() and backgroundRun(), raising the same
            "is this worth the invasiveness" question this file has
            already deferred for BUG-C21.
            (b) Minimal, low-risk fix: wrap executeActions()'s two chunk
            loops so a chunk-level exception is caught, the partial
            trashed/archived/batchMs counts accumulated so far are
            attached to the re-thrown error (e.g.
            `err.partialCounts = {trashed, archived, batchMs}`) before
            re-throwing, and both call sites read `e.partialCounts` in
            their catch blocks to still credit whatever succeeded before
            crediting the error itself. Preserves today's control flow (a
            mid-batch failure still surfaces as an error, still stops the
            rule) while closing the specific accounting gap. The main
            risk is getting the two call sites' catch-block credit logic
            right without duplicating creditStat()'s own semantics
            incorrectly, and deciding whether a "partial success, then
            error" burst should still count as one line in
            stats.labels[lbl] or something visually distinguished from a
            clean success.
            (c) More invasive: make executeActions() itself accept and
            call a `creditPartial(trashed, archived)` callback after
            EVERY chunk (both trash and archive), not just at the end —
            so the caller's own stats object is updated incrementally as
            chunks complete, with nothing left to lose if a later chunk
            throws. Closes the gap most thoroughly (down to per-chunk,
            i.e. worst case 99 threads unreported instead of up to
            several hundred) but changes executeActions()'s calling
            contract for both existing call sites and needs corresponding
            updates to every test that currently asserts on its
            {trashed, archived, batchMs} return shape.
  Why no test was added to claude/Tests this pass
            : Following this project's own established pattern for a
            decision-pending bug (BUG-C19, BUG-E14, BUG-C21 all reproduced
            their finding in a one-off local script or scratch test before
            writing up the bug-plan entry, but did NOT add a permanent
            regression test until a fix direction was chosen — a test
            encoding an accepted bug's behaviour as "correct" would need
            to be rewritten or deleted the moment the bug is actually
            fixed, per this file's own BUG-C13/BUG-C14 lesson about tests
            that encode a bug), this finding was reproduced in a
            throwaway script against this session's local harness (see
            "Reproduced directly" above) rather than committed to
            claude/Tests. Once (b) or (c) above is chosen, the fix pass
            should add a regression test alongside it, the same way every
            single-answer fix in this file (BUG-C15 through BUG-E16) did.
  Not fixed — needs your call on (a)/(b)/(c) before any code changes here.
  See S-N14 in AUTOTRASH_SUGGESTIONS.txt for the cross-reference.

BUG-E17 [LOW] Aborting a run sends an immediate email regardless of
  SUMMARY_FREQ's digest/ERRORS_ONLY mode — unlike a normal completion,
  which defers to the chosen frequency
  File    : Code.gs — abortRun().
  Found   : 2026-09-02, ninth automated pass this session (scheduled "look
            for bugs, fix bugs, write tests, test the code, run a final
            pass" task), while comparing abortRun()'s email-gating logic
            against maybeSendRunEmail()'s (the equivalent gate for a
            normal run completion) side by side.
  Current : maybeSendRunEmail() (used by both finalizeAndEmail(), the
            live-run completion path, and backgroundRun()'s own
            end-of-cycle call) only sends a per-run email immediately in
            two cases: when the run had errors (any freq except NEVER),
            or when SUMMARY_FREQ is literally EACH_RUN. For every OTHER
            frequency — DAILY, ALT_DAYS, WEEKLY, BIWEEKLY, ERRORS_ONLY
            (with no errors) — a normal, error-free run completion sends
            NOTHING immediately; its stats simply accumulate into
            DAILY_STATS for the next scheduled digest (or, for
            ERRORS_ONLY, never surface at all unless something breaks).
            abortRun() does not follow this same gate at all — it sends
            an email whenever `freq !== 'NEVER'`, full stop, with no
            separate check for errors or EACH_RUN:
              if (freq !== 'NEVER') { ... safeMail(...) }
            AUTOTRASH_FEATURE_REFERENCE.txt §4 already documents this
            AS-IS ("Server sends abort email if SUMMARY_FREQ !== 'NEVER'")
            — so this is not a doc/code mismatch, but the reference simply
            states the current behavior without flagging that it is
            inconsistent with how every OTHER email in this project
            behaves, not (currently) a deliberate, documented design
            choice.
  Reproduced directly before writing this entry: a Node repro (this
            session's local test harness) set SUMMARY_FREQ to 'WEEKLY',
            'ERRORS_ONLY', and 'DAILY' in turn and called abortRun() with
            an error-free, non-dry stats object (5 threads moved, no
            errors) — all three configurations sent an immediate
            "⚠ AutoTrash: Aborted..." email, even though none of those
            three frequencies would have sent anything for the exact same
            stats on a NORMAL (non-aborted) completion of the same run.
  Effect  : A user who deliberately chose WEEKLY (or DAILY/ALT_DAYS/
            BIWEEKLY/ERRORS_ONLY) specifically to avoid a flood of
            per-run emails gets exactly the "one email per run"
            experience they opted out of, but only on the runs they
            choose to abort — an inconsistent, mode-defying surprise
            rather than a data-safety problem. Low severity: aborting is
            a deliberate, infrequent user action (not something that
            fires every cycle the way BUG-E14's double-email does on
            1MIN/5MIN), and one could reasonably argue a user-initiated
            abort is itself noteworthy enough to always deserve immediate
            notice regardless of digest preference — which is presumably
            why the code was written this way in the first place, even if
            nothing says so explicitly.
  Why this needs a decision, not just a fix
            : There are two genuinely defensible positions here, not one
            obviously-correct answer (unlike BUG-H15/BUG-H16, which were
            "reject a degenerate input nobody wants" fixes): (1) an abort
            is a deliberate user action mid-run and arguably ALWAYS
            merits an immediate confirmation email no matter the digest
            preference — the current behavior, just undocumented as
            intentional; or (2) an abort should respect SUMMARY_FREQ the
            same way every other email in this project does, for
            consistency, and let the digest (or the next EACH_RUN-style
            immediate email) carry the aborted run's numbers like any
            other run. Picking between them is a product-taste call, so
            per this file's "think it through before touching code" rule
            this is logged rather than patched.
  Options : (a) Do nothing — keep sending an abort email whenever
            freq !== 'NEVER', and make this intentional by adding a line
            to AUTOTRASH_FEATURE_REFERENCE.txt §4 noting explicitly that
            an abort always notifies (except NEVER) regardless of digest
            mode, so a future reviewer doesn't reflag this as a bug.
            (b) Make abortRun() route through the same gate
            maybeSendRunEmail() uses: only send immediately for errors or
            EACH_RUN, otherwise silently accumulate into DAILY_STATS (via
            the existing accumulateDailyStats() call, unaffected either
            way) and let the next scheduled digest report it. Simple,
            small change, but changes user-visible behavior for anyone
            currently relying on "abort always emails me."
            (c) Middle ground: keep the immediate abort email for
            error-free aborts too (since the user just took a deliberate
            action and arguably wants confirmation it registered), but
            make it respect ERRORS_ONLY specifically — i.e. treat
            ERRORS_ONLY the same as EACH_RUN's error branch (only send if
            the aborted run had actual errors), leaving DAILY/ALT_DAYS/
            WEEKLY/BIWEEKLY unaffected since "always notify on
            user-initiated abort" is a more defensible reading for those
            than for "only tell me about errors."
  Not fixed — needs your call on (a)/(b)/(c) before any code changes here.
  See S-N15 in AUTOTRASH_SUGGESTIONS.txt for the cross-reference.

BUG-E12 [LOW] Email animation layer is inert in Gmail and Outlook
  File    : Code.gs — buildEmailHtml() <style> block (FIX 31)
  Current : The @keyframes / .at-* classes only run in WebKit mail clients
            (Apple Mail, iOS Mail). Gmail and Outlook strip <style> blocks
            entirely and render the static inline styles instead.
  Fix     : None available. Animated email is not supportable in Gmail, which
            is where AutoTrash mail actually lands (it sends to the account
            owner). Recorded so nobody re-adds it expecting Gmail support.
  Impact  : None — graceful degradation by design. No fill-mode is set, so a
            client that keeps the stylesheet but blocks animations still shows
            the content rather than leaving it stuck at opacity:0.

BUG-E18 [LOW, dead code] buildEmailHtml()'s per-line color selector still
  checks for two glyphs (─, ▓) that can never occur in any `lines[]` array
  actually passed to it by any of its four real callers — the branch is
  permanently unreachable, a leftover from before the ASCII chart was
  removed from the HTML email body
  File    : Code.gs — buildEmailHtml()'s logHtml color-selection ternary.
  Found   : 2026-09-01, twelfth automated pass this session (scheduled "look
            for bugs, fix bugs, write features, write tests, run a final
            pass" task), while comparing buildAsciiChart()'s actual output
            characters against every caller of buildEmailHtml() side by
            side — an angle no prior pass's review notes mention comparing
            directly.
  Current : buildEmailHtml()'s per-line HTML color logic reads:
              const c = l.startsWith('⚠') || l.startsWith('ERROR') ? '#ff6677'
                      : l.startsWith('✓') ? '#00ff88'
                      : l.startsWith('─') || l.startsWith('▓') ? '#3f7f3f'
                      : l.startsWith('  ') ? '#88bb99'
                      : '#aaffcc';
            The third branch is clearly meant to color ASCII-chart rows —
            '─' is the chart's separator character (buildAsciiChart()'s
            `sep` variable) and '▓' was the chart's OLD fill glyph before
            BUG-R6 (already fixed, see PREVIOUSLY FIXED below) renamed it
            to '█' to match what the chart actually draws. But this
            function's `lines` parameter is populated independently by
            each of its four call sites (abortRun(), sendRunEmail(),
            sendDailyDigest(), sendErrorEmail()) — checked all four
            directly, and NONE of their `lines[]` arrays ever contain an
            element that starts with '─' or '▓'. The one place '▓' does
            appear at all is sendDailyDigest()'s per-label breakdown line
            (`lines.push(\`    ${k}: ${fmtNum(v.moved)} (▓...)\`)`, FIX 22/
            BUG-E3) — but that line starts with four literal spaces, not
            '▓' itself, so it falls through to the `startsWith('  ')`
            branch instead, never this one. The ASCII chart itself (which
            genuinely does start lines with '─', and used to start rows
            with '▓' before BUG-R6) is never part of `lines` at all — it
            is appended separately, only in the PLAIN-TEXT body, by
            plainBody() (S-E4/FIX 35 deliberately dropped it from the HTML
            body entirely, specifically because the per-rule HTML table
            already shows the same split and Gmail clips wide
            white-space:pre content instead of scrolling it). So this
            branch has been unreachable ever since FIX 35 removed the
            chart from any `lines` array reaching this function — and
            BUG-R6's later glyph rename (▓→█) had no observable effect on
            it either, since it was already dead code by that point and
            stayed dead regardless of which glyph it checked for.
  Reproduced directly before writing this entry: grepped Code.gs for every
            '─'/'▓'/'█'/'░' occurrence and traced each of the four
            `lines[]`-building call sites individually (see "Current"
            above) — confirmed none can ever produce a line starting with
            either checked character. Also confirmed in the Node harness
            that buildAsciiChart()'s output is never passed as (or
            concatenated into) the `lines` argument of any `buildEmailHtml()`
            call — only into `plainBody()`'s separate plain-text return
            value.
  Impact  : None — this is inert code, not a behavioral bug. Every email
            this project sends renders identically whether this branch
            exists or not, since it can never be taken. No test can
            meaningfully prove a "before/after" behavior difference the
            way this project's other fixes do (there is no observable
            output to change), which is exactly why this is logged rather
            than "fixed": there is nothing to reproduce as broken, and
            nothing a regression test could assert that isn't already
            covered by the existing HTML-email tests.
  Options : (a) Do nothing — zero user-visible effect either way; leaving
            it costs nothing but a few bytes of ternary nobody will ever
            execute.
            (b) Whenever buildEmailHtml() is next touched for an unrelated
            reason, fold this cleanup in: drop the dead
            `l.startsWith('─') || l.startsWith('▓')` branch entirely
            (folding those lines into the `startsWith('  ')`/default
            cases, which is what they'd resolve to today anyway), or —if
            a future change ever reintroduces per-line chart content into

            where it currently understates the truth.

        getUISettings(), a parse failure is caught by the client's
        .withFailureHandler() (so the page itself doesn't crash), but every
        saved rule would fail to load on every visit with only a generic
        "Load failed" terminal line — no way to recover them from the UI.
        Likelihood is low under normal use (updateSystem() always writes
        valid JSON.stringify() output), but a hand-edited property value,
        a partial write cut off mid-save, or any future code path that
        writes these properties directly rather than through
        updateSystem() could trigger it.
        Fix: both call sites now parse defensively —
        `try { rules = JSON.parse(...); } catch (e) { rules = []; }` (and
        the same for categoryRules) — falling back to an empty list, the
        same safe default already used when the property has never been
        set at all. Covered by
        test_backgroundRun_corruptRulesProperty_doesNotThrow,
        test_backgroundRun_corruptCategoryRulesProperty_doesNotThrow,
        test_getUISettings_corruptRulesProperty_returnsEmptyArraysNotThrow,
        and test_getUISettings_validRulesProperty_stillParsesNormally (the
        last one guards against the fix being over-broad and swallowing
        valid data). The first three were confirmed to FAIL against a
        reverted copy of the pre-fix code.

BUG-C15 [CRITICAL] processLiveBurst's catch block threw a NEW ReferenceError
        on every single exception, silently swallowing the real error.
        Root cause: `const lbl` was declared INSIDE the try{} block and read
        back inside the matching catch{} block as `lbl || 'unknown'`. This is
        not an Apps Script quirk — it's ordinary JS block scoping: a
        const/let declared inside a try{} is not visible from its catch{}.
        Reproduced with a two-line Node script before touching any code:
          try { const x = 1; throw new Error('boom'); }
          catch (e) { console.log(x); }   // ReferenceError: x is not defined
        Effect in production: the moment processLiveBurst() hit ANY runtime
        exception (Gmail quota error, a malformed query, a transient API
        failure — anything), the catch block's own first line
        (`payload.stats.errors.push({ label: lbl || 'unknown', ... })`)
        threw a fresh, unrelated ReferenceError before sendErrorEmail() could
        ever run and before the original error message could be recorded.
        That uncaught ReferenceError propagated out of processLiveBurst()
        entirely, so:
          - No error email was EVER sent for a live-run failure.
          - stats.errors was never populated — BUG-H12's fix (the very line
            sitting right next to this bug) never actually worked for live
            runs, only for backgroundRun() (which declares lbl correctly,
            outside its try block, and was never affected).
          - The client's google.script.run .withFailureHandler() received a
            confusing "lbl is not defined" instead of the real failure
            reason, actively hiding the cause of the problem from the user.
        Fix: `let lbl = 'unknown'` and `let dry = false` are now declared
        BEFORE the try block and reassigned once the rule is known; the
        catch block reads them safely. Verified two ways: (1) a Node
        reproduction of the exact old shape throwing ReferenceError, and (2)
        the new test suite (Tests doc) — reverting this fix locally and
        re-running runAllTests() causes
        test_processLiveBurst_errorDuringLiveRun_recordsErrorAndEmailsWithoutCrashing
        and test_processLiveBurst_errorDuringDryRun_emailReportsProjectedCounts
        to fail with exactly this ReferenceError, confirming the regression
        tests actually catch it.

BUG-E13 [HIGH] Error email during a dry run always showed Trashed/Archived
        as 0/0 instead of the projected dry-run counts.
        Root cause: sendErrorEmail() never received a dryRun flag and always
        passed the raw stats object straight to buildEmailHtml() — but a
        dry run only ever populates stats.dryTrashed/dryArchived, never
        stats.totalTrashed/totalArchived. The exact same bug (BUG-E9) was
        already fixed for the ABORT email; this is the same defect on the
        ERROR email path, which BUG-E9's fix didn't touch.
        Fix: sendErrorEmail() now accepts a 4th `dryRun` argument (passed
        from processLiveBurst()'s catch block, which already knows dry from
        the BUG-C15 fix above). When true, it builds an emailStats copy with
        totalTrashed/totalArchived swapped in from dryTrashed/dryArchived —
        same pattern as abortRun() and finalizeAndEmail() — and tags both the
        subject-adjacent title line and the HTML banner "[DRY RUN]". The
        backgroundRun() caller never dry-runs, so it simply omits the new
        argument and keeps its existing (correct) behaviour.
        Covered by test_processLiveBurst_errorDuringDryRun_emailReportsProjectedCounts.

BUG-C16 [LOW, robustness] processLiveBurst() didn't honour its own
        documented contract for a null activeQueue.
        AUTOTRASH_FEATURE_REFERENCE.txt §11 documents payload.activeQueue as
        "null on first burst, server builds it" — but the function only ever
        checked `if (!payload.activeQueue || ...length === 0) return done:true`.
        In practice this was never hit through the real UI: burst() in
        index.html always pre-builds the queue client-side before the very
        first RPC call, so the documented server-side fallback was dead code.
        But any other caller that took the documented contract at face value
        — including this pass's new test suite — would get an immediate
        "done: true, nothing processed" instead of a working queue.
        Fix: processLiveBurst() now builds payload.activeQueue via
        buildQueue() when it arrives null, exactly mirroring what the client
        already does. Zero behaviour change for the shipped UI (which never
        sends null); makes the function self-sufficient and match its own
        docs. Covered by test_processLiveBurst_builtNullQueueServerSide.
