1. RULE TYPES — WHAT EACH ONE IS AND HOW IT SHOULD WORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1a. CUSTOM LABEL RULES
  Purpose : Target emails by a specific Gmail label (e.g. "newsletters").
  Fields  : label (string), days (int), isTrash (bool)
  Query   : label:"X" in:inbox older_than:Nd -is:starred -in:trash
  Scope   : in:inbox ONLY — ensures archive action is permanent.
            Once archived, label is still on thread but thread is
            no longer in inbox → invisible on next search → stays archived.
  Action  : isTrash === false  → archive
            anything else      → trash   (true OR undefined = trash)
  UI      : User types label name + days + picks Trash/Archive from dropdown.
            isTrash must be set as explicit boolean (never undefined) by addRule().
  Notes   : Label names with spaces must still be passed as-is; buildQuery
            wraps them in quotes automatically. The label text is free-form
            user input with no character restrictions — buildQuery() only
            ever puts it inside a quoted Gmail search term, but if this text
            is ever rendered as HTML (the email per-rule breakdown table is
            the one place it is), it must be HTML-escaped first. See §6's
            note on escHtml() — BUG-E15 in GitHub Issues is the
            regression history for why this matters. Separately, since
            2026-09-01 (BUG-C20), a literal " character inside the label is
            stripped before it goes into the quoted search term itself —
            Gmail search has no escape mechanism for a quote inside a
            quoted phrase, so an unstripped " would have prematurely closed
            the phrase and turned the rest of the label into loose,
            unrelated search terms, silently widening the match. Only the
            search term is affected; the stored/displayed label text (rule
            list, email table) is untouched by this. As of 2026-09-01
            (BUG-H15), addRule() in index.html additionally refuses to save
            a label if stripping every " from it (the same rule
            buildQuery() applies) would leave nothing — a label made ONLY of
            " characters would otherwise sanitize down to an empty Gmail
            search term (label:"" ...) and search with that empty term on
            every run, forever. This is a client-side, save-time guard; it
            does not change what buildQuery() itself does to a label that
            already got saved with at least one non-quote character.
            The "Days" field is also validated at save time — addRule()
            rejects any value under 1 (`d < 1`) — so a label rule can never
            be saved with a zero or negative day count. See §1b for the
            equivalent (and, until 2026-09-01/BUG-H16, missing) guard on
            category rules.

1b. GMAIL CATEGORY RULES
  Purpose : Target Gmail's auto-sorted categories (Promotions, Social,
            Updates, Forums). Also supports Spam (special case).
  Fields  : category (string), days (int), isTrash (bool), enabled (bool),
            isCategory: true (always set by queue builder)
  Defaults: Promotions → 30d → trash
            Social     → 60d → archive
            Updates    → 30d → trash
            Forums     → 60d → archive
            Spam       →  7d → trash
  Query   : Normal categories:
              category:X in:inbox older_than:Nd -is:starred -in:trash
            Spam (special case — not a Gmail tab, lives in in:spam):
              in:spam older_than:Nd -is:starred -in:trash
  Scope   : in:inbox for all non-spam. in:spam for spam.
  Action  : Same isTrash logic as label rules.
  UI      : Toggle card ON/OFF. Fields show when enabled.
            isTrash set by getCatState() from the action dropdown.
            The per-category "Days" number input carries a `min="1"` HTML
            attribute, but that only gates form-level validation, not raw
            keystrokes — a user could type a negative value directly. As of
            2026-09-01 (BUG-H16), getCatState() — the single function every
            read of category state goes through, at render, toggle, and
            save time — floors any non-positive parsed value back to the
            category's documented default, mirroring the guard addRule()
            already has for custom label rules (§1a). Before this fix, a
            negative day count would have been saved and interpolated
            verbatim into buildQuery()'s `older_than:${days}d` term with no
            clamp anywhere server-side either.
  CAUTION (BUG-C19, open — see GitHub Issues): "Archive" for the
            Spam category is suspected to be a silent no-op. Every other
            category is scoped `in:inbox`, so its threads carry the INBOX
            label and "archive" (= remove INBOX label) does what it says.
            Spam is scoped `in:spam` with no `in:inbox`, because spam
            threads normally never carry the INBOX label in the first
            place — so "archiving" one has nothing to remove, the SPAM
            label is untouched, and the thread stays in Spam and keeps
            matching every future run. This has NOT been empirically
            confirmed against a live Gmail account as of this writing;
            treat it as a strong suspicion pending verification, not a
            settled fact. The UI hint text in the Gmail Category Rules
            panel now carries an interim warning about this; the default
            action for Spam remains "Trash" and that default is
            unaffected either way.

2. ENGINE ARCHITECTURE — HOW A RUN WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Since 2026-09-24 the per-rule "search → dedup → act" step described in
  §2a/§2b below is one shared function, runRule() in app/Engine.gs,
  called by both processLiveBurst() and backgroundRun(). Their observable
  behavior (logs, stats, emails, queue handling) is unchanged, with one
  deliberate unification: the live path now registers seenIds BEFORE the
  Gmail move, as the background path already did (FIX 15). This changes
  nothing visible, because a live error halts the run. See
  docs/engine.txt for the stages and how to build on them.

2a. LIVE (MANUAL) RUN — client-driven bursts
  1. User clicks "Engage Engine" in the browser.
  2. launchEngine() builds a queue and a stats skeleton client-side.
  3. burst() sends the payload to processLiveBurst() via google.script.run.
  4. Server processes ONE rule (the head of activeQueue):
       - Searches Gmail (max 500 results)
       - Filters out seenIds (threads already handled this run)
       - If 0 threads remain → eject rule from queue (shift)
       - If dry run         → count what would move, eject rule
       - If live            → execute trash/archive, rotate rule to back
  5. Server returns updated payload + log entries to client.
  6. handleRes() renders log lines, updates stat counters + progress bars,
     and mirrors the full server stats object into `lastStats` (see §4 —
     this is what makes an eventual abort's email/digest accounting
     complete, not just the on-screen counters).
  7. Client calls burst() again with the returned payload.
  8. Repeat until activeQueue is empty → finishEng().
  9. finishEng() calls finalizeAndEmail() server-side then stops.

  Note: the client always pre-builds activeQueue before the FIRST call to
  processLiveBurst() (see burst() in index.html) — the server-side "build it
  when null" path described in §11 exists as a defensive fallback (added
  2026-08-31, BUG-C16) for any caller that doesn't pre-build it, but the
  shipped UI never actually exercises that fallback.

  Coordination (S-N8 / Issue #82 — FIXED 2026-09-24): every live run is
  now registered server-side before its first burst (startLiveRun(), see
  §2e). A second tab/device clicking "Engage Engine" while a run is active
  is refused and shown the active run instead, and registered bursts run
  under the script lock, so two live runs can no longer overlap. Since the
  same date the LAST burst of a registered run also finalizes it
  server-side (finalizeAndEmail() is called inside processLiveBurst()),
  so step 9 no longer depends on the driving tab still being open.

  Scale note (S-N10 in suggestions.txt): payload.seenIds is a
  plain array that grows for the entire life of one run and is serialized
  in both directions on every single burst RPC (see §11's data-flow
  contract) — nothing trims it. For the great majority of runs this is
  negligible, but a single Global/Inbox Purge run against a very large,
  multi-year backlog could grow this into a meaningfully large payload by
  the run's later bursts, which would show up as each burst getting slower
  purely from serialization overhead rather than any actual Gmail work.
  Not fixed; needs a design decision (see S-N10) since the naive fixes
  interact with the seenIds correctness guarantee in §2d/§9.

2b. BACKGROUND RUN — time-trigger driven
  1. Apps Script trigger fires backgroundRun() on schedule (1min–daily).
  2. Reads rules from UserProperties (saved config). Parsed defensively —
     a corrupted AUTOTRASH_RULES/CATEGORY_RULES value falls back to an
     empty list rather than throwing (2026-08-31, BUG-C18); see §10.
  3. Acquires script lock (prevents concurrent executions).
  4. Builds queue, runs while loop until queue empty or 55s budget elapsed.
  5. Each iteration: search → dedup seenIds → execute → rotate.
  6. On completion: accumulateDailyStats + maybeSendRunEmail.
  7. Lock released in finally block.
  8. Next trigger fires automatically — continuous background operation.

  Since 2026-09-24 (Issues #79/#82, see §2e): after taking the lock,
  backgroundRun() skips its firing entirely if a live (manual) run is
  active; otherwise it registers itself in the run registry, publishes its
  engine log/stats after every rule, and checks for a dashboard abort
  request before every rule. An aborted background run still accumulates
  daily stats and sends its run email (status "Background Run (aborted)"),
  and LAST_RUN_TIME gets an "(aborted)" suffix.

  Note: backgroundRun()'s seenIds is a plain in-memory Set scoped to one
  execution's 55s budget — it is never serialized anywhere, so the scale
  note above (S-N10) does not apply to this path, only to the live/manual
  burst path in §2a.

  CAUTION (BUG-C22, open — see GitHub Issues, flagged 2026-09-02,
  ninth pass): step 5's "execute" sub-step (both here and in the live path,
  §2a) calls executeActions(), which chunks its input into GMAIL_CHUNK
  (100)-sized batches and only credits its running trashed/archived
  counters to its own local variables — not yet to the caller's stats
  object — as each chunk's GmailApp call returns. If a LATER chunk throws
  after one or more EARLIER chunks already succeeded (a transient Gmail
  API error or quota limit partway through a large batch), those earlier
  chunks' actions genuinely happened in the mailbox, but executeActions()
  throws before ever returning its {trashed, archived, batchMs} object —
  so the caller (processLiveBurst() or backgroundRun()) never learns the
  partial count, and it never reaches stats.totalTrashed/totalMoved,
  creditStat(), DAILY_STATS, or the resulting error email's own "Moved:"
  line. No wrong Gmail action results — see §7's note on this bug for the
  full impact — but this is a genuine gap in this section's own guarantee
  that "each iteration: search → dedup seenIds → execute → rotate" fully
  and accurately reports what "execute" did.

  CAUTION (BUG-C23, open — see GitHub Issues, flagged 2026-09-02,
  tenth pass): step 6's "accumulateDailyStats" call happens while
  backgroundRun() still holds the ScriptLock from step 3 — so it is
  correctly serialized against a SECOND backgroundRun() execution. It is
  NOT serialized against sendDailyDigest() (§6), which is a completely
  separate trigger function that never acquires this (or any) lock before
  reading, emailing, and resetting the very same DAILY_STATS property. A
  digest send that lands while a backgroundRun() execution is mid-flight
  can have its reset silently overwritten by that backgroundRun()'s own
  accumulation (which read the pre-reset value) — re-including an
  already-emailed period's totals in the next one — or, in the opposite
  ordering, lose that backgroundRun()'s real contribution outright. See
  BUG-C23 for a concrete reproduction of the exact mechanism. This is
  separate from, and does not interact with, backgroundRun()'s own
  ScriptLock guarantee against overlapping WITH ITSELF — that guarantee is
  intact and unaffected.

2c. ROUND-ROBIN ROTATION
  - After successfully processing a batch, the rule is moved to the BACK
    of the queue: queue.push(queue.shift()).
  - This gives every rule a fair turn; no single large rule starves others.
  - A rule is only EJECTED (removed entirely) when it returns 0 threads.
  - Gmail search caps at 500 results per call. If a rule has >500 matches,
    it will process 500 then rotate, returning on the next cycle for more.
    This rotate-and-return behaviour is what lets a LIVE run fully drain an
    arbitrarily large backlog over successive bursts — see §3's note on
    why a DRY run, which never rotates, does not get the same guarantee.

2d. SEENIDS DEDUPLICATION
  - payload.seenIds (live) / seenIds Set (background) tracks thread IDs
    processed by ANY rule during the current run.
  - Before acting, each rule filters out seenIds from its search results.
  - Prevents a thread matched by rule A from being re-actioned by rule B.
  - seenIds lives only for the duration of one run; next run starts fresh.
  - This is critical for archive correctness: without it, a trash rule
    could find and trash a thread that an archive rule already archived.


2e. CROSS-DEVICE RUN REGISTRY (app/RunState.gs, added 2026-09-24)
  Purpose: any run — manual from any tab/device, or background from the
  trigger — is visible on, abortable from, and (manual runs) resumable on
  every open dashboard. Closes S-N8 (Issue #82) and S-N3 (Issue #79).

  Storage:
    RUN_STATE (UserProperties) — id, source (live|background), dryRun,
      status (running|done|aborted|error), driverId (tab driving a live
      run), startedAt, updatedAt (heartbeat), current rule, rules left,
      log seq, endedAt, endMsg.
    RUN_ABORT (UserProperties) — id of the run an abort was requested for.
      Separate key so an abort can't be lost to a concurrent RUN_STATE write.
    RUN_DETAIL_<id> (UserCache, 6h) — last 150 log lines, full stats, rule
      list for progress bars.
    RUN_PAYLOAD_<id> (UserCache, 6h) — the live run's latest burst payload,
      for resuming. If it would exceed the 100 KB cache cap, it is saved
      without seenIds (a resume then starts a fresh dedup set — see §2d;
      Gmail moves are idempotent, a dry run may slightly over-count).

  Liveness: a run is ACTIVE while status=running and its heartbeat is
  newer than 90 s (live) / 150 s (background). A live run past that is
  shown as PAUSED (driver tab closed / phone locked) and can be resumed or
  aborted; a background run past that was cut off by Apps Script's own
  time limit and is simply replaced by the next trigger firing.

  Server API (google.script.run):
    getRunStatus(sinceSeq, runId) — polled by every dashboard; returns the
      run, new log lines since sinceSeq, stats, rule list, LAST_RUN_TIME,
      serverNow (clients correct clock skew with it).
    startLiveRun(meta) — registers a live run; refused while another run is
      active (returns that run).
    requestAbort(runId) — sets RUN_ABORT. The run's own driver stops at
      its next checkpoint (next burst / next background rule) and finalizes
      as a normal abort (§4). If the run is stale (no driver left), the
      request finalizes it itself.
    claimRun(runId, driverId) — take over / resume a live run: waits for any
      in-flight burst (script lock), returns the latest saved payload, and
      the old driver's next burst is answered superseded:true.
    pauseBackgroundTrigger() — sets TRIGGER_MODE to OFF and re-syncs
      triggers (same path as Save Config), for "Abort + Pause Trigger".

  All writers of RUN_STATE hold the script lock; readers and requestAbort
  don't, so dashboards stay responsive while a burst runs.

3. DRY RUN MODE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  - Toggled by "Dry Run" button before clicking Engage Engine.
  - Each rule is processed exactly ONCE then ejected (never rotated).
  - No Gmail actions are executed (no trash, no archive).
  - Counts go into dryTrashed / dryArchived (not totalTrashed/totalArchived).
  - Purge rules route their projected counts through creditStat() into
    globalPurge*/inboxPurge*, exactly as on the live path — never stats.labels.
  - totalMoved IS incremented (for display purposes — "would action N").
  - UI stat counters sv1/sv2 show dryTrashed/dryArchived during the run.
  - Summary email uses dryTrashed/dryArchived (FIX 6).
  - Abort email uses dryTrashed/dryArchived (FIX 11).
  - An error email fired mid-dry-run also uses dryTrashed/dryArchived, not
    0/0 (BUG-E13, fixed 2026-08-31 — the same swap FIX 11/BUG-E9 already
    applied to the abort email, extended to the error-email path).
  - Daily stats are NOT accumulated for dry runs (FIX 10) — this now applies
    consistently on BOTH the normal-completion path (finalizeAndEmail) and
    the abort path (abortRun), see §4.
  - After run, isDry state is preserved — user must toggle off manually.
  - CAUTION (BUG-C21, open — see GitHub Issues, flagged
    2026-09-01, eighth pass): because a dry-run rule is processed exactly
    once and never rotated (unlike a live rule — see §2c), its reported
    "would trash/archive" count is capped at whatever ONE
    `GmailApp.search(q, 0, GMAIL_SEARCH)` call returns, i.e. at most 500 —
    even if the rule's true backlog is far larger. A live run of the same
    rule still correctly drains the full backlog over multiple bursts via
    round-robin rotation, so this does not cause any wrong Gmail action or
    lost mail; it only means a dry-run preview can meaningfully understate
    how much a live run will actually move for any single rule matching
    more than 500 threads. Not fixed — needs a decision on whether to
    surface the truncation (e.g. label the count "500+" when the cap was
    hit) or actually close it (page through search results within one dry
    pass, at the cost of a longer single RPC call) before any code changes.

4. ABORT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  - User clicks "⛔ Abort" during a live run.
  - Sets aborted=true, running=false client-side immediately.
  - Calls server abortRun(lastStats, elapsedMs, isDry) — see below for
    lastStats.
  - Server saves LAST_RUN_TIME with "(aborted)" suffix.
  - For a LIVE (non-dry) abort, the server now also calls
    accumulateDailyStats() before anything else (2026-08-31, BUG-C17) — any
    real Gmail actions taken in the bursts before the abort are rolled into
    DAILY_STATS exactly as they would be on a normal completion. A DRY-RUN
    abort still skips this entirely, matching FIX 10 (nothing real happened,
    so nothing should be counted). This call is subject to the same
    unsynchronized-DAILY_STATS caution as backgroundRun()'s own call — see
    BUG-C23 in §2b/§6/§7.
  - Server sends abort email if SUMMARY_FREQ !== 'NEVER'. CAUTION (BUG-E17,
    open — see GitHub Issues, flagged 2026-09-02, ninth pass): this
    is the ONLY gate abortRun() applies — unlike maybeSendRunEmail() (§6),
    which only sends an email immediately for an error-free run when
    SUMMARY_FREQ is literally EACH_RUN, and otherwise defers to the next
    scheduled digest. abortRun() sends immediately for EVERY frequency
    except NEVER, including WEEKLY/DAILY/ALT_DAYS/BIWEEKLY/ERRORS_ONLY, even
    when the aborted run had no errors — an inconsistency with how every
    other email in this project behaves, not (currently) a deliberate,
    documented design choice. Whether "an abort always notifies" should
    stay as-is or should respect SUMMARY_FREQ the way a normal completion
    does is an open decision — not fixed.
  - Abort email shows projected trash/archive if dry run (FIX 11), and now
    includes the same per-rule breakdown table every other email type gets
    (2026-08-31, BUG-H13 — previously always empty on the abort email; see
    "lastStats" below).
  - The currently-in-flight burst may still complete server-side
    (Google can't cancel mid-execution), but no further bursts fire.
  - Since 2026-09-24, abortRun() takes the run's id as a 4th argument. With
    it, the abort waits for an in-flight burst to finish (script lock),
    uses the server's own recorded stats if they are more complete than the
    caller's (so a burst whose reply the tab never saw is still counted),
    marks the run aborted for every dashboard, and is idempotent — an abort
    arriving from two devices emails/accumulates once.
  - Abort from another device: requestAbort() (§2e). The driving tab's next
    burst returns abortRequested:true and it runs the normal abort above.
    Background runs stop before their next rule; "Abort + Pause Trigger"
    also sets the trigger to Manual only so the next firing doesn't restart
    it.

  lastStats (client, index.html): a full-fidelity mirror of the last stats
  object returned by processLiveBurst() — labels, purge sub-counts, errors,
  everything. Distinct from `runStats`, which only ever tracks the three
  on-screen totals (plus dry mirrors) and is what actually drives the stat
  counters. Before 2026-08-31 (BUG-H13), doAbort() sent the reduced
  `runStats` to the server, so the abort email's per-rule table was always
  empty — and once BUG-C17 added daily-stat accumulation to the abort path —
  those per-rule/purge sub-counts would still have been missing from
  DAILY_STATS for any aborted run. doAbort() now sends `lastStats ||
  runStats` (the fallback covers an abort clicked before the very first
  burst response arrives).

5. BACKGROUND TRIGGER MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  OFF     : Manual runs only. No background trigger.
  1MIN    : Most aggressive. Each execution = 55s burst. Continuous cleanup.
            Uses ScriptLock to prevent overlapping executions.
  5MIN    : Same as 1MIN but less frequent.
  15MIN   : Moderate frequency.
  HOURLY  : Low frequency, suitable for light maintenance.
  DAILY   : Runs once at 1am. Single burst only.

  ScriptLock behaviour:
    - waitLock(5000) — waits up to 5s to acquire.
    - If another instance holds the lock → log and return (skip this run).
    - Queue emptiness is checked BEFORE acquiring the lock to avoid
      holding it when there's nothing to do.
    - Lock is always released in finally{} block.
    - This lock ONLY ever guards backgroundRun() against a second
      backgroundRun() execution overlapping it. It does NOT guard against
      sendDailyDigest() (§6) reading/resetting DAILY_STATS concurrently —
      see BUG-C23 (GitHub Issues, flagged 2026-09-02, tenth pass)
      and the CAUTION note in §2b for the resulting race.

  KNOWN GAP (tracked as BUG-E14, not yet fixed — see GitHub Issues):
    a rule that throws inside backgroundRun()'s loop sends an immediate
    per-error email AND is still counted in the end-of-cycle summary email
    (which fires whenever stats.errors is non-empty, regardless of
    SUMMARY_FREQ except NEVER) — so one failure can produce two emails per
    cycle. On 1MIN/5MIN this repeats every cycle until the rule is fixed.

6. SUMMARY EMAILS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  EACH_RUN    : Email after every live run (background or manual).
  DAILY       : Accumulate all day, send digest once daily at digestHour.
  ALT_DAYS    : Digest every 2 days.
  WEEKLY      : Digest every 7 days.
  BIWEEKLY    : Digest every 14 days.
  ERRORS_ONLY : Only send if a run encountered errors.
  NEVER       : No emails at all (including abort emails).

  maybeSendRunEmail() gate (applies to a NORMAL run completion — live via
  finalizeAndEmail(), or background's own end-of-cycle call): sends
  immediately only when the run had errors (any frequency except NEVER) or
  when SUMMARY_FREQ is literally EACH_RUN; every other frequency with an
  error-free run sends nothing immediately and simply lets
  accumulateDailyStats() carry the numbers into the next scheduled digest.
  abortRun() does NOT go through this same gate — see §4's BUG-E17 note for
  the resulting inconsistency on an aborted run specifically.

  Digest emails:
    - Sent by sendDailyDigest(), triggered by a separate daily time trigger.
    - That trigger is created for ANY digest frequency, independent of
      TRIGGER_MODE — manual-only users accumulate stats too and must still
      receive them. sendDailyDigest() returns early when runs === 0, so an
      idle account sends nothing.
    - Reads accumulated DAILY_STATS from UserProperties.
    - After sending, resets DAILY_STATS for the next period.
    - CAUTION (BUG-C23, open — see GitHub Issues, flagged
      2026-09-02, tenth pass): this read-then-send-then-reset sequence
      shares no lock with accumulateDailyStats() (called by backgroundRun()
      and finalizeAndEmail()/abortRun()), which performs its own
      unsynchronized read-modify-write against the same DAILY_STATS
      property. A digest that fires while a backgroundRun() execution is
      also touching DAILY_STATS can have its reset silently clobbered by
      that backgroundRun()'s accumulation (re-including the just-emailed
      period's totals in the next one) or can itself wipe out a
      backgroundRun()'s real contribution before it's ever counted — see
      §2b's CAUTION note and BUG-C23 for the concrete reproduction. Not
      fixed; needs a decision on whether to share backgroundRun()'s
      ScriptLock, add a narrower dedicated lock, or leave as-is.
    - digestHour controls the send time (6am–8pm, configurable). The UI
      dropdown now offers all 15 valid hours (6–20) — a former gap
      (previously only 6, 7, 8, 9, 12, 18, 20 were offered) closed
      2026-08-31 (FIX 43 / S-N5 in suggestions.txt). Purely a UI
      change; the backend has always accepted any integer 6–20.
    - An aborted LIVE run's real actions now correctly contribute to
      DAILY_STATS too (2026-08-31, BUG-C17/BUG-H13) — previously an abort
      silently excluded everything it had actually done from every digest.
    - DAILY_STATS does NOT accumulate an errors count/list at all — only
      run/moved/trashed/archived/purge totals and the per-label breakdown
      (see accumulateDailyStats() in §10). A digest email therefore never
      reports how many errors occurred during its period, even though the
      per-run stats object it's built from always carries one. Flagged as
      S-N12 in suggestions.txt (2026-09-01) rather than fixed —
      immediate per-error emails already exist (see the BUG-E14 gap just
      above in §5), so this may be intentional; needs a decision.

  Email format:
    - Dark-theme HTML with stat boxes (Actioned / Trashed / Archived).
    - Dry run emails: stat boxes relabelled "Would Action / Would Trash / Would Archive";
      amber "SIMULATION ONLY — NO MAIL WAS MOVED OR DELETED" banner above header.
    - Per-rule table with colour-coded split bar (red=trash, blue=archive).
      As of 2026-08-31 this table is populated on the abort email too — it
      was always empty there before (BUG-H13).
    - Rule names in that table are HTML-escaped via escHtml() before being
      interpolated into the row markup (2026-09-01, BUG-E15) — a rule name
      is free text the user typed into the "Label name" field in index.html
      with no character restrictions, and every other piece of dynamic text
      in the email (the operation-summary lines below the table) was already
      escaped; this closed the one gap where it wasn't. Any future spot that
      interpolates a label/rule name — or any other user-supplied string —
      into this email's HTML must go through escHtml() the same way.
    - ASCII chart appears in the PLAIN-TEXT fallback only. It was removed from
      the HTML body: the table above shows the same split, and Gmail strips
      overflow-x so wide charts clipped instead of scrolling. As of
      2026-09-01 (twelfth pass), the per-line color-selection logic inside
      buildEmailHtml() (used for the operation-summary lines below the
      per-rule table) still contains a branch checking for two characters
      that only the ASCII chart ever produces ('─' and the chart's
      pre-BUG-R6 '▓' glyph) — but since the chart itself never reaches the
      `lines[]` array this function receives (only plainBody()'s separate
      plain-text output gets it), that branch is permanently unreachable.
      This is harmless dead code, not a behavior bug — see BUG-E18 in
      GitHub Issues for the full trace; logged there rather than
      fixed since there is no observable output to change either way.
    - Plain text fallback (built by plainBody()) included in all emails.
    - Digest plain-text now includes per-rule breakdown lines matching the HTML table.
    - The ERROR email (sendErrorEmail(), separate from the run-summary
      emails above — fired immediately when a rule throws) has its own
      "Rule:" line naming the failing rule. As of 2026-09-01 (BUG-E16),
      that line is guaranteed to name the same rule as the corresponding
      stats.errors[] entry, including for a category rule with no `.label`
      field (which falls back to its uppercased category id, same as
      everywhere else in this file). Both callers (processLiveBurst() and
      backgroundRun()) pass their own already-correct rule name into
      sendErrorEmail() explicitly now, rather than letting it re-derive one
      without that fallback — see GitHub Issues BUG-E16. CAUTION
      (BUG-C22, open, flagged 2026-09-02): this "Rule:" line's own "Moved:"
      figure is sourced from stats.totalMoved, which — per §2b/§7's note —
      can itself under-report by however many threads a partially-succeeded
      chunk batch actually moved before a later chunk threw. The rule name
      is guaranteed correct (BUG-E16); the moved count next to it is not
      always guaranteed complete.
    - As of 2026-09-01 (BUG-C24, eleventh pass), sendErrorEmail() no longer
      assumes the thrown value is a real Error object with a `.message`
      property — it normalizes whatever was actually thrown (`errMsg =
      (err && err.message) ? err.message : String(err)`) before building
      the "Message :" line or the subject line's `.substring(0, 60)`. GmailApp
      and the other Apps Script services this project calls are documented
      to throw proper Error instances, and normally do, but nothing in the
      JS language or this codebase enforced that — a bare `throw` of a
      string or plain object anywhere upstream used to crash
      sendErrorEmail() itself with a TypeError before it ever reported the
      real failure, the same failure shape as BUG-C15 (an error-reporting
      path that throws a new, unrelated error and hides the original one).
      See BUG-C24 in GitHub Issues for the full mechanism.

7. STATISTICS & DAILY ACCUMULATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Per-run stats object fields:
    totalMoved      — all threads actioned (trash + archive, or dry scan total)
    totalTrashed    — live trash count only
    totalArchived   — live archive count only
    dryTrashed      — projected trash count (dry runs only)
    dryArchived     — projected archive count (dry runs only)
    globalPurgeMoved / globalPurgeTrashed
    inboxPurgeMoved  / inboxPurgeTrashed
    labels{}        — per-rule breakdown: { moved, trashed, archived, finished }
                      keyed by the rule's display label (rule.label, or the
                      uppercased category id as a fallback). See §1a and the
                      NOTE at the end of this section — a custom label rule
                      whose text collides with another rule's key (e.g. a
                      literal "PROMOTIONS" custom label alongside the
                      Promotions category) shares one entry and one email
                      row between two logically distinct rules; tracked as
                      S-N11 in suggestions.txt.
    globalPurgeDone / inboxPurgeDone
                    — bool, set when a purge rule ejects. Purge rules get no
                      stats.labels entry, so these are the only "finished"
                      signal the client has for their progress bars.
    errors[]        — { label, error } for any rule that threw. This is the
                      one place a category rule's fallback name
                      (rule.category.toUpperCase()) and the error email's
                      own "Rule:" line are required to agree — see §6's
                      BUG-E16 note; before 2026-09-01 they could disagree
                      for a category rule with no `.label` field. As of
                      2026-09-01 (BUG-C24), the `error` field itself is also
                      guaranteed to be a real string even when the thrown
                      value has no `.message` property — previously a
                      non-Error throw stored a literal `undefined` here,
                      which would have printed as the text "undefined" in
                      any downstream email/digest listing stats.errors.

  Daily stats (stored in UserProperties as JSON):
    Accumulated by accumulateDailyStats() after each live run — this
    includes an ABORTED live run (2026-08-31, BUG-C17): abortRun() now
    calls accumulateDailyStats() itself for non-dry aborts, mirroring what
    finalizeAndEmail() has always done for normal completions. Only a
    DRY-RUN abort (or a dry-run normal completion) skips it.
    DRY RUNS DO NOT accumulate (FIX 10).
    Reset ONLY after a digest email is sent — never on a calendar-day
    boundary, or ALT_DAYS / WEEKLY / BIWEEKLY periods would lose every day
    but the last one. accumulateDailyStats() updates the date field as a
    last-updated marker and initialises only when the stored object is empty.
    CAUTION (BUG-C23, open — see GitHub Issues, flagged
    2026-09-02, tenth pass): accumulateDailyStats() (called from
    backgroundRun(), finalizeAndEmail(), and abortRun()) and
    sendDailyDigest()'s own read-send-reset cycle both perform unsynchronized
    read-modify-write against this same property — backgroundRun()'s
    ScriptLock only ever guards against a second backgroundRun() execution,
    never against a concurrent sendDailyDigest() trigger firing. See §2b/§6
    for the full caution and BUG-C23 for a concrete reproduction of the
    resulting race.
    Fields: date, runs, totalMoved, totalTrashed, totalArchived,
            globalPurgeMoved, globalPurgeTrashed,
            inboxPurgeMoved,  inboxPurgeTrashed,
            labels{} (same shape as per-run labels). Notably absent: any
            errors field — see §6's note on S-N12.

  creditStat() routing:
    - isGlobalPurge → globalPurgeMoved / globalPurgeTrashed
    - isInboxPurge  → inboxPurgeMoved  / inboxPurgeTrashed
    - everything else → stats.labels[lbl]
    CAUTION (BUG-C22, open — see GitHub Issues, flagged 2026-09-02,
    ninth pass): creditStat() itself is correct — the gap is upstream. Both
    callers only invoke creditStat() with whatever executeActions() managed
    to RETURN, and executeActions() returns nothing at all (it throws
    instead) if any chunk after the first one fails — so a rule whose first
    chunk succeeded and second chunk failed gets creditStat() called zero
    times for that burst/cycle, even though the first chunk's action really
    happened. See §2b and §6 for the same caution from the executeActions()
    and email-reporting angles respectively.

  NOTE (2026-09-01, fifth pass): stats.labels is a plain object keyed by
  string label text, with nothing enforcing uniqueness across custom label
  rules and enabled categories. Two rules that happen to produce the same
  key (identical custom label text, or a custom label that happens to match
  an enabled category's uppercase display name) silently merge their counts
  into one stats.labels entry and one row in the per-rule email table and
  digest. This does not affect what Gmail actually does — each rule's
  buildQuery()/action still runs correctly and independently — only the
  reporting layer conflates the two. Not fixed; see S-N11 in
  suggestions.txt for options.

8. UI / FRONTEND BEHAVIOUR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Header        : Version badge, last-run timestamp (updated after each run).
                  An amber "(DRY)" tag follows the timestamp when the run that
                  just finished was a simulation.
  Stats row     : Actioned / Trashed / Archived / Rules Left / Elapsed.
                  Counters flash on update. "live" class animates colour bar.
                  Rules Left = activeQueue.length from the last burst response;
                  seeded with the full queue size at launch, 0 at completion.
  Panels        : System Config and Gmail Categories start COLLAPSED on load;
                  Custom Label Rules starts open (most actively managed).
  Terminal      : Scrolling log. Each line: timestamp | badge | message.
                  BATCH lines are emitted ONCE per action type per burst, not
                  once per 100-thread chunk (a 500-thread rule logs one line).
                  Badge colours: SEARCH=blue, RESULT=amber, ACTION/DONE=green,
                  DRYRUN=amber, ERROR=red, INFO=dim-green (g3), BATCH=dim-green.
                  SEP level renders as a faint full-width horizontal rule with no
                  badge, no timestamp, and no text — purely visual section divider.
                  Banners (ok/warn/err) shown at key milestones.
                  Terminal is capped at 300 nodes; oldest 50 trimmed on overflow.
  Rule display  : Top-right of terminal shows the CURRENT rule being processed.
                  Updates after each burst response (round-robin tracking).
  Progress bars : One bar per rule. Width advances as threads are actioned.
                  Turns solid green + "done" class when rule ejects cleanly.
                  Purge bars read globalPurgeMoved/inboxPurgeMoved for width
                  and globalPurgeDone/inboxPurgeDone for the done state.
                  A ✓ is prefixed to the rule name once it ejects clean.
                  All bars jump to 100% on run completion.
                  Bars are keyed by cid(label) — see S-N6 in
                  suggestions.txt for a rare label-collision edge case.
  Orb           : Green pulsing dot = engine running. Dim = idle/stopped.
  Watching      : (2026-09-24, §2e) Every dashboard polls getRunStatus() —
                  every 2.5 s while showing a run, 10 s while idle, 20 s while
                  driving, never while the page is hidden (resumes on
                  visibility). A run from another tab/device or the trigger
                  takes over the stats, terminal (with its server log, in
                  local clock time), progress bars and elapsed timer, with a
                  status-bar tag: OTHER DEVICE / PAUSED / BACKGROUND.
                  Buttons while watching: Abort (becomes "Aborting…" until
                  the run stops, or "Force Stop" if its driver went silent);
                  "Take Over" (active live run, asks first) / "Resume Here"
                  (paused live run); "Abort + Pause Trigger" (background
                  run). The run's ending banner shows on every watching
                  dashboard. The header's LAST RUN also refreshes from the
                  poll (S-N3).
  Connection loss : A driving tab whose burst RPC fails re-syncs from the
                  server's saved payload (claimRun with its own id) and
                  retries up to 3 times before stopping; the run then shows
                  as paused and can be resumed on any device.
  Mobile / cross-browser : (2026-09-24) The viewport is set in doGet() via
                  HtmlOutput.addMetaTag() — HtmlService ignores a viewport
                  <meta> inside index.html, which is why phones rendered the
                  desktop layout shrunk down. The Save / Dry Run / Abort /
                  Engage row is pinned to the bottom of the screen on every
                  size. Native select/number/button chrome is stripped and
                  redrawn identically in Chrome, Safari and Firefox
                  (color-scheme:dark, one custom select arrow, no number
                  spinners); inputs are 16px on phones so iOS doesn't zoom
                  on focus; Engage/Dry Run hide on phones during a run
                  (they are disabled anyway).
  Traffic dots  : Red + yellow opacity raised during run, dimmed when stopped.
  Dry Run tag   : Amber "DRY RUN" badge shown in status bar when active.
  Save Config   : Saves rules + category states + all system settings.
                  Does NOT trigger a run.
  Abort button  : Only visible while engine is running. Disabled after click
                  while abort RPC is in flight. Sends `lastStats` (the full
                  server-returned stats object, see §4) rather than the
                  reduced on-screen `runStats` (2026-08-31, BUG-H13).
  Add Rule      : addRule() validates the label + day count before pushing a
                  new custom label rule. As of 2026-09-01 (BUG-H15) it also
                  refuses a label that would strip down to an empty string
                  once buildQuery() removes every literal " character from
                  it (mirroring that exact sanitization client-side) — a
                  label made only of " characters would otherwise save
                  successfully but search Gmail with an empty label term
                  forever. Any label with at least one non-quote character
                  is unaffected.
  Category days : getCatState() (backs the toggle/render/save paths for the
                  Gmail Category Rules panel) floors any parsed "Days" value
                  under 1 back to the category's documented default, the
                  same guard addRule() already applies to custom label
                  rules. As of 2026-09-01 (BUG-H16) this also catches a
                  negative value typed directly into the field — the
                  input's `min="1"` HTML attribute alone does not block
                  keystrokes, only form-level validation, so a manually
                  typed negative number previously sailed through
                  unclamped into the saved rule and from there into
                  buildQuery()'s `older_than:${days}d` term.
  Design language : (2026-09-24) One shared UI shell in index.html — see the
                  "UI SHELL" block at the end of its <script>. New pages or
                  features should use it rather than their own versions:
                  - Motion tokens (--dur-fast 120ms / --dur-normal 200ms /
                    --dur-slow 320ms, --ease-standard/enter/exit; JS mirror
                    MOTION + motionOK()). prefers-reduced-motion zeroes them
                    and resolves every animation to its end state.
                  - Status pill (setState) in the header: READY / STARTING /
                    RUNNING / DRY RUN / WATCHING / PAUSED / ABORTING /
                    COMPLETE / DRY COMPLETE / ABORTED / HALTED.
                  - Run pipeline under the terminal bar: RULES → SEARCH →
                    EVALUATE → EXECUTE → DONE. A stage lights only when the
                    server log reports it (SEARCH; RESULT/DRYRUN/clean-eject
                    COMPLETE; ACTION/BATCH/DONE) — never on a timer. EXECUTE
                    shows "–" on dry runs; a stage never reached shows "–" at
                    completion; the active stage shows ✕ on abort/error.
                  - Execution summary ("AUTOTRASH // RUN #<id tail>") below
                    the completion banner: rules queued, Gmail searches,
                    threads found, duplicates skipped (if any), starred
                    excluded, trash/archive (or would-trash/would-archive),
                    total, errors (stats.errors), elapsed. Search/found lines
                    are omitted when this tab only saw part of the run's log
                    (resumed here, or the watched log tail was trimmed).
                  - Counters count up to new values (countTo) and flash once;
                    a rule's progress row flashes when its actioned count
                    rises.
                  - uiConfirm() dialog replaces native confirm(): Global
                    Purge gate (§9) and Take Over / Resume a live run — same
                    conditions as before, Cancel focused by default on
                    destructive dialogs, Esc/backdrop cancel.
                  - toast(msg, kind) with ok/warn/err accents; Save Config
                    shows Saving… → ✓ Saved on the button.
                  - Removed as constant/decorative motion: CRT scanline
                    overlay, Engage button's idle pulse; header cursor now
                    blinks 3× on state changes instead of forever; glow
                    reduced.
  Completion banner : Shown in the terminal when a run ends. Both the live
                  ("✓ COMPLETE") and dry-run ("[DRY RUN COMPLETE]") variants
                  report the same figures — total actioned/scanned, the
                  trash/archive split, how many rules actually moved
                  something (ruleCount), and elapsed time. Before
                  2026-09-01 (BUG-H14) the live banner omitted ruleCount
                  even though it was already computed for exactly this
                  purpose and the dry-run banner right next to it already
                  used it — a plain oversight, now fixed so both banners
                  carry the same detail.

9. SAFETY RULES — WHAT AUTOTRASH WILL NEVER TOUCH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  - Starred emails (-is:starred in all queries). No exceptions. This is a
    hard guarantee — do not add per-rule overrides without revisiting §9.
  - A live run with Global Purge active cannot start without an explicit
    confirmation from the user (see §1d) — since 2026-09-24 the shared
    uiConfirm() "DESTRUCTIVE ACTION" dialog rather than a native confirm().
  - Emails already in trash (-in:trash in all queries except global purge,
    where the scope already excludes trash via Gmail's search behaviour).
  - Emails matched by rule A that have already been actioned by rule A
    or any earlier rule in the same run (seenIds dedup).
  - The user's drafts, sent mail, chats — none of these appear in the
    label/category/inbox searches used by AutoTrash. FIXED (2026-09-25,
    found in review, no issue number filed): this was true for every rule
    type EXCEPT Global Purge, which deliberately has no in:inbox scope (so
    it can also reach archived mail) and, as a side effect nothing here
    excluded, was searching Gmail's "All Mail" scope — which includes the
    user's own Sent mail (and Drafts). A Global Purge could silently trash
    year-old Sent mail right alongside old received mail, undisclosed in
    either the Global Purge UI copy or its DESTRUCTIVE-ACTION confirmation
    dialog. buildQuery()'s isGlobalPurge branch now also excludes
    -in:sent -in:drafts, closing the gap without narrowing what Global
    Purge is meant to reach (received mail, inbox or archived). See
    test_buildQuery_globalPurge_excludesSentAndDrafts in
    tests/RuleEngine.test.gs.

10. CONFIG STORAGE (UserProperties keys)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Schema-driven since 2026-09-24: every setting readConfig()/writeConfig()
  handle is declared once in CONFIG_SCHEMA (app/Config.gs) as
  {key, prop, type, default, backup?, countKey?, countFn?} — readConfig(),
  writeConfig() and parseStoredRules() all walk that list generically
  instead of naming each field inline. Adding a future setting is one
  CONFIG_SCHEMA entry; nothing else in Config.gs needs to change. This is
  purely an internal reorganization — every PropertiesService key name and
  JSON-vs-string format below is unchanged, because app/Runner.gs and
  app/EmailSend.gs read SUMMARY_FREQ/GLOBAL_PURGE_DAYS/INBOX_PURGE_DAYS
  directly via props.getProperty(), bypassing readConfig() entirely.

  AUTOTRASH_RULES   — JSON array of custom label rule objects. Read
                      defensively — a corrupted value falls back to []
                      rather than throwing (2026-08-31, BUG-C18). Since
                      2026-09-24 both readers (getUISettings()/readConfig()
                      in Config.gs, and backgroundRun() in Runner.gs) go
                      through one shared parseStoredRules() (Config.gs)
                      instead of two separately-maintained try/catch pairs.
                      CONFIG_SCHEMA marks this field backup:true (see
                      CONFIG BACKUP / RESTORE below).
  CATEGORY_RULES    — JSON array of category rule objects. Same defensive
                      parsing as AUTOTRASH_RULES. Also backup:true.
  TRIGGER_MODE      — string: OFF / 1MIN / 5MIN / 15MIN / HOURLY / DAILY
  SUMMARY_FREQ      — string: EACH_RUN / DAILY / ALT_DAYS / WEEKLY /
                               BIWEEKLY / ERRORS_ONLY / NEVER
  GLOBAL_PURGE_DAYS — string: OFF or number of days
  INBOX_PURGE_DAYS  — string: OFF or number of days
  DIGEST_HOUR       — string: hour number (6–20)
  LAST_RUN_TIME     — string: human-readable timestamp of last run
  RUN_STATE         — JSON: the current/last run's registry record (§2e).
                      Read defensively — corrupt reads as "no run".
  RUN_ABORT         — string: id of the run an abort was requested for (§2e)
  LAST_DIGEST_DATE  — string: ISO date of last digest email sent. FIXED
                      (Issue #98, 2026-09-25): an unparseable stored value
                      (hand-edited, corrupted, or from a future format
                      change) used to make sendDailyDigest()'s daysSince
                      computation NaN, which made `should send?` latch at
                      false FOREVER for every SUMMARY_FREQ except DAILY —
                      and since that early return happens before this
                      property is ever rewritten, the corrupted value never
                      self-corrected. sendDailyDigest() now treats an
                      unparseable date the same as "never sent"
                      (daysSince = Infinity), so a corrupted value heals
                      itself on the very next check instead of permanently
                      silencing the digest.
  DAILY_STATS       — JSON: accumulated stats for current digest period.
                      Already parsed defensively (try/catch → {}) since
                      before this pass — accumulateDailyStats() and
                      sendDailyDigest() both guard it. CAUTION (BUG-C23,
                      open, flagged 2026-09-02): defensive PARSING is not
                      the same as safe CONCURRENT access — the two writers
                      of this key (accumulateDailyStats() and
                      sendDailyDigest()) share no lock with each other; see
                      §2b/§6/§7 for the resulting race.

  CONFIG BACKUP / RESTORE (2026-09-24) — fixes a live-reported bug: a Save
  Config click could silently replace a non-empty rule set with an empty
  one if the initial settings load had failed or was still in flight (the
  in-memory `rules`/`catState` default to empty until a load succeeds, and
  the old failure handler only logged the error instead of blocking saves).
  Two independent layers now guard against this:
    - AUTOTRASH_CONFIG_BACKUPS — JSON array (newest first, capped at
      CONFIG_BACKUP_MAX = 5) of prior snapshots of every CONFIG_SCHEMA
      field marked backup:true (today: rules, categoryRules). Written by
      snapshotConfigBackup() (app/Config.gs) at the TOP of every
      writeConfig() call, i.e. it captures the state right before it's
      about to be overwritten. Skipped (no backup written) when the
      pre-write state is already empty, so a fresh install or an
      already-empty config doesn't pile up useless snapshots. A quota
      failure while writing this key never blocks the real config write —
      snapshotConfigBackup() drops backups oldest-first until the value
      fits, and gives up quietly if even one alone won't fit.
      listConfigBackups() returns summaries only (a count per backed-up
      field, via that field's countKey/countFn — e.g. ruleCount,
      categoryCount — no rule bodies), and restoreConfigBackup(ts) restores
      every backup:true field from one snapshot, leaving every other
      setting untouched; restoring itself snapshots the pre-restore state
      first, so a restore is undoable the same way a normal save is.
    - Client-side (index.html): Save Config refuses to run at all until
      the initial getUISettings() load has actually succeeded
      (`configLoaded`), and — separately — shows a "SAVE WILL REMOVE ALL
      RULES" uiConfirm() dialog before any save that would take a
      previously non-empty rule/category count down to zero, so the
      mistake is caught before it's written, not just recoverable after.
      A "Restore a Backup…" button in the System Config panel opens a
      picker (showBackupPicker()/renderBackupPicker()) listing each
      backup's summary and relative age (relTime()); restoreFromBackup()
      confirms, calls restoreConfigBackup(), and updates the in-memory
      rules/categories from the result.

11. DATA FLOW: CLIENT ↔ SERVER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Client sends payload to processLiveBurst():
    {
      dryRun:          bool,
      rules:           [...],           // saved label rules
      categoryRules:   [...],           // all category states
      globalPurgeDays: 'OFF' | string,
      inboxPurgeDays:  'OFF' | string,
      activeQueue:     [...] | null,    // null on first burst, server builds it
      seenIds:         [...],           // thread IDs already processed this run
      stats:           { ... }          // running totals, carried across bursts
    }

  Server returns:
    {
      payload: { ...updated payload },  // returned for next burst call
      log:     [ {t, level, msg} ],     // log lines to render in terminal
      done:    bool,                    // true when all rules ejected
      ejected: bool,                    // true when a rule was just removed
      moved:   number,                  // threads actioned this burst
      error:   bool,                    // true on exception
      msg:     string                   // status message
    }

  The entire run state lives in payload, passed back and forth.
  Server is stateless between bursts — all state must be in payload.

  Registered runs (2026-09-24, §2e): the shipped UI also sends
  runId + driverId in the payload. The server then additionally keeps a
  copy of the post-burst payload (for resume) and may answer with
  { busy } (lock contention — client retries in 1 s), { superseded }
  (another device took over — stop driving), { abortRequested } (abort
  from another device — run the local abort path), or add
  { finalized:true, lastRun } on the final burst (server already emailed
  and wrote LAST_RUN_TIME — the client must not call finalizeAndEmail()).
  A payload without runId behaves exactly as described above.

  "server builds it" (2026-08-31, BUG-C16): processLiveBurst() now actually
  does this — previously a null activeQueue just short-circuited to
  done:true with nothing processed, contradicting this paragraph. The client
  (burst() in index.html) has always pre-built the queue before the first
  call regardless, so this had no effect on the shipped UI; it matters for
  any other caller, including the test suite, that sends null as documented.

  Separately from this per-burst payload, the client also keeps a
  `lastStats` reference — a plain mirror of the most recent
  `res.payload.stats` object, used only when the user aborts (see §4). It
  is not sent back to the server as part of the next burst; it exists
  purely so abortRun() has the same full stats shape finalizeAndEmail()
  already gets.

  Scale note (S-N10 in suggestions.txt): because seenIds is a
  field of `payload` (not `stats`) and the whole payload round-trips on
  every burst, seenIds is the one field in this contract whose size is
  unbounded by design across a very large run. See §2a for the detail; not
  fixed, flagged as a suggestion for a future design decision.
