1. WHY tests/ LOOKS THE WAY IT DOES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Through 2026-09-23 the entire suite lived in one file, tests/Tests.gs
(1224 lines: framework, spies, and all 89 test functions). On 2026-09-24
it was split into one file per app/*.gs file it tests, mirroring app/'s
own layout, plus a Node-runnable harness was added so the suite can run
without an Apps Script account at all. Both changes shipped together in
one PR (#94) since the split was what made the harness's file layout
make sense in the first place.

There are now two ways to execute the exact same test run — not two
implementations of testing, one implementation invoked two ways:

  1. Apps Script editor: open the project, select runAllTests in
     RunAll.gs, Run ▶. Uses the REAL GmailApp / PropertiesService /
     LockService / ScriptApp / Session. Emails an HTML report to the
     script owner in addition to writing the execution log.

  2. Node, from a clone of this repo, no Apps Script account needed:
         npm test
     (equivalently: node tests/harness/run-node-tests.js)
     Loads every app/*.gs + tests/*.gs file into one Node `vm` context
     seeded with mocked Apps Script services, then calls that SAME
     runAllTests(). This is how a change should be verified locally —
     by a human, or by an AI agent immediately after writing code —
     before it's ever pushed.

Both paths call tests/RunAll.gs's runAllTests(). Nothing about the test
logic itself differs between them; only what backs GmailApp et al.
differs (real Apps Script services vs. the mocks in
tests/mocks/apps-script-globals.js).

tests/TestFramework.gs
  The framework every other test file depends on. Contains:
    - assert(cond, msg), assertEqual(actual, expected, msg)
      (JSON.stringify comparison), assertThrows(fn, msg)
    - withSavedProps(keys, fn) — saves a UserProperties key, runs fn(),
      restores the original value (or deletes the key if it never
      existed) even if fn() throws. Every test that touches
      PropertiesService wraps its body in this.
    - makeFakeThread(id) — a fake Gmail thread: {__id, __trashed,
      __archived, getId()}.
    - makeRichFakeThread(id, data) — makeFakeThread plus the GmailThread
      read methods the engine's message context uses (getMessages,
      getFirstMessageSubject, getLabels, ...), each call counted in
      __calls so a test can prove expensive data was never fetched.
    - freshStats() — a zeroed stats object matching the shape
      processLiveBurst()/backgroundRun() build for themselves.
    - installGmailSpy(searchImpl) — reassigns the global GmailApp to a
      fake with search/moveThreadsToTrash/moveThreadsToArchive/
      sendEmail, tracking calls.{search,trashBatches,archiveBatches,
      emails}. searchImpl can be a plain array (same result for every
      query) or a function(query) => threads[]. Returns
      {calls, restore()}.
    - installLockSpy(opts) — reassigns the global LockService.
      opts.failToAcquire simulates lock contention. Returns
      {wasReleased(), restore()}.
    - installScriptAppSpy(existingTriggers) — reassigns the global
      ScriptApp, faking getProjectTriggers/deleteTrigger/newTrigger with
      a fluent builder (.timeBased().everyMinutes/everyHours/everyDays/
      atHour().create()). Returns {calls, triggers(), restore()}.
  Also holds one self-test (test_assertThrows_frameworkHelperWorks) —
  a test of the framework, not of app/ — and its own TESTFRAMEWORK_TESTS
  array (1 entry).

  buildTestFns() concatenates every suite's array into one list:

        return []
          .concat(TESTFRAMEWORK_TESTS)
          .concat(UTILS_TESTS)
          .concat(RULEENGINE_TESTS)
          .concat(ENGINE_TESTS)
          .concat(STATS_TESTS)
          .concat(EMAILTEMPLATES_TESTS)
          .concat(EMAILSEND_TESTS)
          .concat(CODE_TESTS)
          .concat(CONFIG_TESTS)
          .concat(RUNNER_TESTS)
          .concat(RUNSTATE_TESTS);
      }
  and defines runAllTests() — the single implementation both the Apps
  Script editor and the Node harness call. runAllTests() calls
  buildTestFns() as its first line (2026-09-24 fix, BUG: see below) —
  the list is NOT a top-level const. Iterates the result, times each
  test, collects {name, status, ms, error, stack}, logs to the console,
  emails an HTML+plain-text report via safeMail(ownerEmail(), ...), and
  returns {passed, failed, total, results}.

  BUG FIX (2026-09-24): TEST_FNS was originally a top-level
  `const TEST_FNS = [].concat(TESTFRAMEWORK_TESTS, ...)`, built once
  when RunAll.gs itself loaded. That threw "ReferenceError:
  TESTFRAMEWORK_TESTS is not defined" when run from the real Apps
  Script editor — Google's runtime executes each file's top-level
  statements in an order it picks for itself (observed to be roughly
  alphabetical, which runs "RunAll.gs" before "TestFramework.gs"), and
  a `const` in one file is NOT usable from another file's top-level
  code until that file's own top-level code has actually run — sharing
  one execution scope does not mean every top-level assignment across
  every file happens before any of them runs. The Node harness never
  caught this: run-node-tests.js hardcodes TestFramework.gs and every
  *.test.gs to load before RunAll.gs (see WHY ONE CONCATENATED SCRIPT
  below), which happened to match what the fix now guarantees for real.
  Moving the concat into buildTestFns() and calling it from inside
  runAllTests() means it only runs when someone actually invokes
  runAllTests() — by which point every file's top-level code has
  already executed, in the Apps Script editor or the Node harness
  alike, regardless of file order either runtime happens to pick.

tests/harness/check-index-html.js  (Node-only — never pushed to Apps
                                     Script; see §5; added 2026-09-30,
                                     regex-literal scanner fix 2026-10-01)
  A boot-safety guard on app/index.html's inline <script> content, called
  by run-node-tests.js right after runAllTests() and folded into the same
  `npm test` exit code, but reported as its own summary line ("AutoTrash
  index.html guard: N/N passed") rather than added to the runAllTests()-
  suite count above (see the current running total at the top of §2). It
  is NOT a tests/*.test.gs suite because it needs Node's real `fs` (to
  read index.html off disk) and `vm` (to compile extracted script text)
  directly — capabilities the sandboxed Apps-Script-mock vm context every
  *.test.gs suite runs in does not expose, and which the real Apps Script
  editor has no equivalent of either (there is no local index.html file
  to read there).

  Why it exists: neither this test suite nor
  .github/workflows/syntax-check.yml looked at index.html's inline
  scripts at all before this file existed — syntax-check.yml's
  syntax-check job only runs `node --check` on app/*.gs and tests/*.gs,
  and run-node-tests.js's APP_FILES list only loads app/*.gs into its vm
  context. That gap is exactly how the live Apps Script deployment broke
  on 2026-09-25 ("Uncaught SyntaxError: Unexpected token 'class'", fixed
  in 6d6dc5d/c6a288c): a template literal nested inside another template
  literal's `${...}` interpolation in renderSummary(), which parsed fine
  in Node and Chromium (so nothing local caught it) but broke on the
  served copy.

  Two checks per inline <script> block found (scripts with a `src`
  attribute, if any are ever added, are skipped — nothing local to read
  for those):
    1. `vm.Script` compiles the block's text (syntax only) — catches any
       real parse error, not just this one known pattern.
    2. A static scanner walks template-literal spans tracking `${...}`
       depth and flags any backtick found while already nested inside
       such an interpolation — the shape that broke live even though it
       is syntactically valid JS.

  Proof: running checkIndexHtmlSource() against `git show
  b06f449:app/index.html` (the commit right before the fix) reports 4/5
  passed, 1 failed, flagging the exact `data-to="${r[1]}"` nested
  backtick at its correct line/col. The same check against the current
  file passes 5/5.

  2026-10-01 fix (code review `claude/autotrash-review/
  review-20261001.md`, Project knowledge): the scanner originally had no
  concept of regex literals, so any backtick inside a regex (e.g. `/`/`)
  was read as a template-literal boundary. A stray backtick in a regex
  ANYWHERE earlier in a <script> block could desync the nesting tracker
  for everything after it and make the guard silently miss a REAL nested
  `${ \`...\` }` bug later in the same block (reported a clean pass on an
  adversarial script built to contain exactly that). Fixed by tracking
  the standard "previous significant token" heuristic to tell `/`
  division from the start of a regex literal, then skipping to the
  regex's own closing `/` (honoring `[...]` character classes and escaped
  slashes) without touching the template-nesting stack at all. See
  tests/harness/check-index-html.selftest.js for the regression coverage
  (the adversarial case plus checks that the fix doesn't make the scanner
  over-eager on ordinary division). `app/index.html` currently has no
  regex literal containing a backtick, so the bug was dormant in
  practice, but the guard's whole purpose is catching a repeat of a real
  outage, and it was failing silently rather than erroring.

3. ADDING A TEST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Any change to backend behavior (app/) must get a matching test in the
SAME pass — not a follow-up.

  1. Find the tests/*.test.gs file matching the app/*.gs file you
     changed (app/RuleEngine.gs → tests/RuleEngine.test.gs, etc).
  2. Write the test function using assert/assertEqual/assertThrows and,
     if it touches Gmail/Lock/ScriptApp/PropertiesService, the relevant
     spy/helper from TestFramework.gs.
  3. Add the function to that file's own `..._TESTS` array. RunAll.gs
     picks it up automatically from there — nothing else to register.
  4. Run `npm test` and confirm it passes (and that the total count
     went up by exactly the number of tests you added).
  5. If the new test needs a spy/helper that doesn't exist yet, add it
     to TestFramework.gs, not to the individual test file — every other
     suite may want it too.

4. HOW THE NODE HARNESS ACTUALLY WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Apps Script's real runtime effectively concatenates every .gs file in a
project into one shared global scope — a function or const declared in
one file is visible from every other file, in any push/file order. The
harness's job is to reproduce that faithfully enough that a test behaves
identically whether it runs in the real editor or under Node.

run-node-tests.js:
  1. Builds a Node `vm` context (a Node built-in — not a dependency) via
     vm.createContext(sandbox), where sandbox = createGlobals() from
     tests/mocks/apps-script-globals.js (GmailApp, PropertiesService,
     LockService, ScriptApp, Session, HtmlService, CacheService, console).
  2. Reads every app/*.gs file, then every tests/*.gs file, and
     concatenates ALL of their source text into ONE string — in this
     order: app/Code.gs, app/Utils.gs, app/Config.gs, app/RuleEngine.gs,
     app/Engine.gs, app/Stats.gs, app/RunState.gs, app/Runner.gs, app/EmailSend.gs,
     app/EmailTemplates.gs, then
     tests/TestFramework.gs, tests/Utils.test.gs,
     tests/RuleEngine.test.gs, tests/Engine.test.gs, tests/Stats.test.gs,
     tests/EmailTemplates.test.gs,
     tests/EmailSend.test.gs, tests/Code.test.gs, tests/Config.test.gs,
     tests/Runner.test.gs, tests/RunState.test.gs,
     tests/RunAll.gs (RunAll.gs must be last — see the note below on
     why).
  3. Runs that single concatenated string as one vm.Script via
     script.runInContext(context) — ONE compilation, not one per file.
  4. Calls context.runAllTests() and prints a CLI-friendly pass/fail
     summary, exiting 0 iff every test passed (1 otherwise).

WHY ONE CONCATENATED SCRIPT, NOT ONE runInContext() CALL PER FILE
  This is the one genuine gotcha in the whole harness, worth
  understanding if you ever touch run-node-tests.js: top-level `const`/
  `let` declarations in a script executed via vm's runInContext do NOT
  attach to the shared context (global) object — only `var` and
  function declarations do. If each file were loaded as its own
  separate vm.Script().runInContext(context) call, every top-level
  `const X_TESTS = [...]` (every tests/*.test.gs file, plus GMAIL_CHUNK
  and friends in app/Code.gs) would be invisible to any LATER script.
  Concatenating into a single script before evaluation sidesteps that
  Node-specific mismatch entirely.
  (Function declarations DO attach to the context object even split
  across separate scripts, which is why runAllTests() itself — a
  function declaration — is reachable as context.runAllTests() after
  the fact regardless; it's specifically top-level const/let that this
  affects.)

  CORRECTION (2026-09-24): this section used to claim the real Apps
  Script runtime has "no equivalent problem" here because it "really
  does share one execution scope across files" — that's true of the
  end state (every top-level const does end up attached to the shared
  scope eventually) but false about ORDER: Apps Script still executes
  each file's top-level statements in an order it picks for itself
  (observed to be roughly alphabetical), one file at a time, so a
  top-level statement in file A that reads a `const` from file B still
  throws a ReferenceError if A happens to run before B — the real
  runtime's OWN version of exactly the mismatch this section describes,
  not something the Node harness invented. tests/RunAll.gs hit this for
  real (TESTFRAMEWORK_TESTS undefined when RunAll.gs ran before
  TestFramework.gs) — the fix there was to stop building TEST_FNS at
  top level at all (buildTestFns(), called from inside runAllTests()
  itself; see the tests/RunAll.gs section above), which sidesteps file
  order in BOTH runtimes rather than relying on either one's load
  order to happen to come out right — this harness's hardcoded
  TEST_FILES order above happened to mask the bug rather than avoid it,
  which is why Node's 139/139 didn't catch what the Apps Script editor
  hit immediately.

MOCKS — WHAT'S FAKE VS. WHAT'S REAL (tests/mocks/apps-script-globals.js)
  GmailApp / LockService / ScriptApp: baseline no-ops only. Every test
  that actually exercises their behavior overrides them itself via
  installGmailSpy()/installLockSpy()/installScriptAppSpy() from
  TestFramework.gs — exactly as it does in the real Apps Script editor,
  where those same spies reassign the same globals. The baseline exists
  purely so a test that forgets to install a spy fails on a wrong
  assertion instead of a confusing TypeError.
  PropertiesService / Session: real, working implementations. Nothing
  in the suite spies over these (getProps()/ownerEmail() are called
  directly), so PropertiesService is backed by an actual in-memory
  Map-based key/value store for the lifetime of one harness run —
  behaviorally equivalent to a real UserProperties store across one
  runAllTests() execution — and Session.getEffectiveUser().getEmail()
  returns a fixed fake address, 'test-owner@example.com'.
  createGlobals() returns a FRESH object on every call, so separate
  `npm test` invocations never leak state — though within one run all
  92 tests still share one PropertiesService store, same as they'd
  share one real UserProperties store across one Apps Script
  runAllTests() execution. This is exactly why every property-touching
  test wraps itself in withSavedProps() — it's what keeps 92 tests
  sharing one store from stepping on each other.

5. DEPLOYMENT — WHAT REACHES THE LIVE APPS SCRIPT PROJECT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Only .gs/.html files belong in the live Apps Script project — Apps
Script has no notion of a package.json, a node_modules/, or a plain .js
file as source. .claspignore excludes everything except app/**/*.gs,
app/*.html, tests/**/*.gs, and appsscript.json, so `clasp push` (or a
manual copy-paste) never tries to ship package.json,
tests/mocks/apps-script-globals.js, or tests/harness/run-node-tests.js
into the editor. Those three files — and node_modules/ if it exists
locally — are Node-only tooling that supports the second way of running
the suite (§1) and nothing else; they have no effect on the live
mailbox-cleanup behavior.

A GitHub push is still not a deploy (see CLAUDE.md's Rules) — this
applies to test-only changes exactly as much as it does to app/
changes. Landing a new test in tests/*.test.gs on GitHub does not make
it visible in the Apps Script editor until the next clasp push or
manual copy-paste of the tests/*.gs files.

has two jobs:
  - syntax-check: node --check --input-type=commonjs on every app/*.gs
    and tests/*.gs file (stdin-piped to dodge Node's
    ERR_UNKNOWN_FILE_EXTENSION for the unrecognized .gs extension —
    this only confirms valid JavaScript syntax, nothing behavioral).
  - test-suite: actually runs `npm test` — i.e. the full test suite,
    via the exact same harness described in §4. This job did not exist
    before 2026-09-24; before that, CI could only confirm the test
    files parsed, not that the tests themselves passed, since the
    suite had no way to run outside the Apps Script editor.
